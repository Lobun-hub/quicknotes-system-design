# QuickNotes relational data model

QuickNotes uses PostgreSQL. Each user's notes and tags are owned by that user;
the API derives ownership from the authenticated identity rather than accepting
an arbitrary owner ID from a client.

## Entities and relationships

- **users** stores account identity and authentication data. Its `id` is the
  primary key.
- **notes** stores a user's note content. Each note has one owning user, so
  `users` to `notes` is a one-to-many relationship (`notes.user_id` references
  `users.id`).
- **tags** stores a user's reusable labels. Each tag has one owner, so
  `users` to `tags` is also one-to-many (`tags.user_id` references `users.id`).
- **note_tags** is the join table for notes and tags. It has a composite
  primary key and foreign keys to both parent tables, implementing a
  many-to-many relationship: a note can have multiple tags, and a tag can
  label multiple notes.

All IDs are UUIDs generated by the application. Deleting a user cascades to
their notes and tags; deleting a note or tag cascades to its join rows. The
service deletes a note in the database and relies on the `note_tags.note_id`
foreign key's `ON DELETE CASCADE` to remove its associations in the same
transaction. Tags remain available to their owner for use on other notes. The
service verifies that a note and tag have the same owner before creating a
join row.

## PostgreSQL schema

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email VARCHAR(320) NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE notes (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(100) NOT NULL CHECK (char_length(trim(title)) > 0),
    body TEXT NOT NULL DEFAULT '',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tags (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name VARCHAR(50) NOT NULL CHECK (char_length(trim(name)) > 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (user_id, name)
);

CREATE TABLE note_tags (
    note_id UUID NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
    tag_id UUID NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (note_id, tag_id)
);
```

## Indexes

```sql
CREATE INDEX notes_user_updated_idx
    ON notes (user_id, updated_at DESC, id);

CREATE INDEX note_tags_tag_note_idx
    ON note_tags (tag_id, note_id);
```

The notes index supports the primary list operation (a user's notes ordered by
most recently updated) without scanning other users' rows. The join-table
index supports finding every note that uses a given tag; the primary key
already supports looking up tags for a particular note.

## Example queries

List the most recently updated notes for one user:

```sql
SELECT id, title, body, created_at, updated_at
FROM notes
WHERE user_id = $1
ORDER BY updated_at DESC, id
LIMIT $2;
```

Fetch a note and its tags in one query (JOIN):

```sql
SELECT n.id AS note_id, n.title, n.body, t.id AS tag_id, t.name AS tag_name
FROM notes AS n
LEFT JOIN note_tags AS nt ON nt.note_id = n.id
LEFT JOIN tags AS t ON t.id = nt.tag_id
WHERE n.id = $1
  AND n.user_id = $2
ORDER BY t.name;
```

Create a tag association only if both resources belong to the caller, then
return the note's tags:

```sql
INSERT INTO note_tags (note_id, tag_id)
SELECT n.id, t.id
FROM notes AS n
JOIN tags AS t
  ON t.id = $2
 AND t.user_id = n.user_id
WHERE n.id = $1
  AND n.user_id = $3
ON CONFLICT (note_id, tag_id) DO NOTHING;
```

Count a user's notes by tag, including notes that have no tags:

```sql
SELECT t.id, t.name, COUNT(nt.note_id) AS note_count
FROM tags AS t
LEFT JOIN note_tags AS nt ON nt.tag_id = t.id
WHERE t.user_id = $1
GROUP BY t.id, t.name
ORDER BY t.name;
```

## SQL vs. NoSQL

PostgreSQL is a good fit because notes, users, tags, and their associations
have clear relationships and ownership rules that benefit from foreign keys
and transactions. The service needs reliable joins for tagged-note views and
constraints to prevent orphaned or duplicate relationships. Notes can still
store flexible text in a `TEXT` column; a document database would add
duplication and consistency work without a compelling advantage for this
workload. If future telemetry shows a different access pattern, non-critical
derived views can be added without weakening the source-of-truth constraints.
